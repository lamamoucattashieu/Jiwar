A one-off Node container builds the UI into a volume that nginx serves on port 8080. Passwords come from `.env`, which is git-ignored. |

Prompt: [docs/ai-prompts/part1-foundation.md](docs/ai-prompts/part1-foundation.md) | Claude Code | On startup each service connects to SQL Server, retrying while Azure SQL wakes from auto-pause, then applies any new `migrations/NNN_*.sql` file in its own transaction and records its checksum, so an edited old migration stops startup. A lock stops two instances migrating at once. The UI sends the chosen demo user in `X-Demo-User`; `requireRole` checks the role on the server. Course rules sit in `courseService.js` and use a repository interface, with a SQL version and an in-memory version for tests. Errors we expect return a clear message and status; anything else returns a generic 500 without internals. `/health` never touches the database so it can pause. I checked it with the tests, `docker compose up`, the browser in Arabic on a phone-sized screen, and with the learning service stopped. Testing caught three AI mistakes: the driver rejected `mssql://` URLs, the log showed `/6` instead of `/courses/6`, and the handoff zip had Windows-only paths. |

Prompt: [docs/ai-prompts/part2-ci-cd.md](docs/ai-prompts/part2-ci-cd.md) | Claude Code | `ci.yml` runs on every pull request: lint, format check, tests that fail below 70% coverage, `npm audit`, the UI build and both Docker builds. When a pull request is merged, `cd.yml` runs CI again, pushes both images to GHCR tagged with the commit SHA, signs in to Azure as our managed identity with OIDC (no password stored anywhere), points both Container Apps at the new images and waits until `/health` reports that SHA, which also proves the migrations ran on startup. Then it builds the UI with a `config.js` holding the Azure addresses, uploads it to the Static Web App, runs a read-only smoke test against the live URLs (databases, catalogue, deep links, CORS from our UI only) and tags the commit `release-YYYY.MM.DD-N`. The Bicep file declares every Azure resource; `setup.sh` runs it once, creates one database user per service and connects GitHub to Azure. I checked the workflows with actionlint, the scripts with shellcheck, compiled the Bicep, ran every CI step on a clean checkout, and ran the health and smoke scripts against docker compose, including runs where they must fail. The clean CI run found two real problems the AI had introduced in part 1: zod 3.23.8 and React Router 7.1.1 have high-severity advisories (upgraded to 4.6.7 and 7.18.6), and three files were not formatted. The Azure deploy itself could not be tested before setup.sh is run with the group's access. |
