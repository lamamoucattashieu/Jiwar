# Decision Records

## ADR-1: Two services, learning and projects, each built as ports and adapters

- **Status:** Accepted, Sprint 0 (17 Nov 2026); internal structure added in Sprint 2 (22 Nov 2026)
- **Context:** The assignment requires exactly two services, each with its own container and database, talking over HTTP. Jiwar has two clearly separate jobs: training youth in coding and AI, and matching them to paid projects from local businesses. Inside each service, business rules (who may edit a course, what a trainee may see) must be testable without SQL Server, because coverage is measured on the core logic.
- **Decision:** Split along that line. The **learning** service owns courses and learner progress. The **projects** service owns businesses, project offers and applications. When the projects service needs to know what a learner has completed, it asks the learning service over HTTP (`LEARNING_URL`) instead of reading its database. Inside each service, every feature is a module with a service (the rules), a repository port with two adapters (SQL Server for production, in-memory for tests and for running without `DATABASE_URL`), a zod schema and thin Express routes. Errors meant for the user are `HttpError`s; anything else returns a generic 500 with no stack trace. When one change must trigger others (a verified credit recalculates the level, which notifies the trainee), the change writes an event to an `outbox` table in the same database transaction, and a dispatcher delivers it to in-process handlers (Observer), retrying failures on later runs.
- **Alternatives:** One service per user type (youth vs. business), which would split the same data across both services and need many cross-service calls; a single monolith, which the assignment does not allow. For the follow-up work, calling the handlers directly after saving, which loses the follow-up if the process stops in between, and a message broker, which the assignment does not allow. Inside a service, queries written directly in route handlers, which is shorter but mixes HTTP, rules and SQL and needs a database for every test.
- **Consequences:** Each service can be built, tested and deployed by a sub-team on its own, and adding a feature means adding a module. Calls from projects to learning need a timeout and a clear error when learning is down. Referential integrity across the seam (a learner ID stored in projects) is checked in code, not by a foreign key. Most tests run in milliseconds with no database; the SQL adapters are checked with a fake executor, and against real SQL Server through `docker compose` and the deployed smoke test.

## ADR-2: Node.js (Express), Azure SQL serverless and migrations on startup

- **Status:** Accepted, Sprint 0 (17 Nov 2026); migrations added in Sprint 2 (22 Nov 2026)
- **Context:** The backend must be Python (Flask or FastAPI) or Node.js (Express). Storage must be Azure SQL Database serverless on Azure and SQL Server locally, with the schema defined by versioned migration files applied on startup. Azure SQL serverless pauses when idle, needs up to a minute to resume, and only pauses if nothing queries it.
- **Decision:** Both services use Node.js 24 with Express 5. Each service has its own SQL Server database (`learning`, `projects`) and its own login with access to that database only. Locally one SQL Server container holds both databases, created by the idempotent `db/init.sql`. Each service has a `migrations/` folder of plain SQL files named `NNN_description.sql`. On startup the service connects (retrying while the database resumes), applies the files it has not run yet, each in its own transaction, and records them in `schema_migrations` with a SHA-256 checksum. An application lock (`sp_getapplock`) stops two instances migrating at once. `GET /health` does not touch the database, so probes do not keep it awake; `GET /health/db` runs `SELECT 1`.
- **Alternatives:** FastAPI (Python), which would mean two languages in the repository; a shared database with one schema per service, which the assignment does not allow; an ORM's migration tool (Prisma, Knex), which adds a dependency and its own conventions for a handful of SQL files; running migrations as a separate pipeline step, which would need the pipeline to reach the database directly.
- **Consequences:** One language for the UI and both services, so everyone can review every pull request. Node's built-in test runner gives tests and coverage without extra packages. Migrations are ordinary SQL Server SQL (`INT IDENTITY`, `NVARCHAR`, `OFFSET … FETCH`) that anyone can read in a pull request; a mistake in an applied migration is fixed with a new migration, never by editing the old one, because a changed checksum stops startup. The first request after a long idle period is slow while the database resumes.

## ADR-3: React (Vite) static UI with runtime configuration

- **Status:** Accepted, Sprint 0 (17 Nov 2026)
- **Context:** The UI must be static files on Azure Static Web Apps, calling both services from the browser. Service URLs differ between local and Azure and must not be hardcoded.
- **Decision:** React built with Vite to static files in `ui/`. Service URLs live in `ui/public/config.js` (`window.JIWAR_CONFIG`), loaded before the app. The local file points to `localhost`. On deploy the pipeline overwrites it with the Azure Container Apps URLs. Locally, compose builds the UI once (`ui-build`) and serves it with a stock `nginx:alpine` image, with no Dockerfile.
- **Alternatives:** Plain HTML/JS, which is simpler but harder to grow as the number of pages increases; Vite build-time variables (`import.meta.env`), which would require a rebuild per environment.
- **Consequences:** The same build works everywhere. Each service only accepts cross-origin requests from the UI's origin (`CORS_ORIGIN`).

## ADR-4: Demo users instead of authentication

- **Status:** Accepted, Sprint 0 (17 Nov 2026)
- **Context:** User authentication is out of scope; a hard-coded demo user is enough.
- **Decision:** The product uses a small set of seeded demo users (learners and businesses). The UI lets the presenter pick which demo user to act as. Calls between the two services (eligibility checks and project credits) use `/internal` endpoints that require a shared key in the `X-Internal-Key` header, stored as a Container Apps secret. Projects calls learning with a 3-second timeout and a circuit breaker, so a learning outage fails only the features that need it, with a clear message.
- **Alternatives:** An optional API key, which protects write endpoints but does not help show both sides of the product in the demo; real authentication, which is out of scope.
- **Consequences:** No passwords or sessions to store or secure. The live system is not fit for real users without adding authentication.

## ADR-5: Bicep for the one-time setup, GitHub Actions with OIDC for every deploy

- **Status:** Accepted, Sprint 2 (22 Nov 2026)
- **Context:** Every merge to `main` must deploy both services and the UI to Azure, only if CI passed, apply migrations, and fail if `/health` does not return 200. Nothing may be changed by hand after the initial setup. The group's resource group, region (`westeurope`) and managed identity (`<prefix>-github`) already exist; we cannot create resource groups or assign roles.
- **Decision:** `infra/main.bicep` declares the Log Analytics workspace, the Container Apps environment, both Container Apps (0 to 1 replicas), the SQL server with two serverless databases (15-minute auto-pause, 2 GB) and the Static Web App. `infra/setup.sh` runs it once, creates one contained user per database, registers the identity's federated credentials and sets the GitHub secrets and variables. `ci.yml` runs on every pull request and branch push: lint, format check, tests with a 70% coverage floor, `npm audit` and image builds. `cd.yml` runs on every push to `main`: it calls `ci.yml`, pushes both images to GHCR tagged with the commit SHA, signs in to Azure with OIDC (no stored password), points both Container Apps at the new images, waits until `/health` reports that SHA (the services migrate on startup), deploys the UI with a generated `config.js`, runs a read-only smoke test against the live URLs, and tags the commit `release-YYYY.MM.DD-N`.
- **Alternatives:** The Azure CLI commands typed by hand and copied into the README, which works but cannot be re-run or reviewed as code; running Bicep on every deploy, which would need the SQL administrator password in every pipeline run; a client secret for a service principal, which IE accounts cannot create and which would need rotating.
- **Consequences:** The whole Azure setup is reviewable and repeatable, and every production version maps to a commit and a release tag. The first deploy fails until both GHCR packages are made public (Azure cannot pull private images without credentials). Re-running setup keeps the images CD deployed. Revisions run in single mode, so a deploy briefly restarts each service; a canary with traffic splitting is a possible next step.
